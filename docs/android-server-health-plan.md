状态：实验方案 v0.9；用户已在小米 14 确认 0.1.0 功能正常，反馈键盘遮挡、状态栏重叠、背景与设置缺失。0.2.0 已补原生安全区域/键盘动画、桌面动态天气背景与服务器可编辑设置；键盘修复仍需新包真机复验。健康每 2 小时同步已启用，AI 健康分析仍关闭。

当前范围：先交付可安装的 Kotlin + WebView 手机试用版：文字聊天、7 个模型配置、服务器历史、健康看板与同步。104 条桌面历史一次性导入且在手机只读；完整桌面双向自动同步、附件、技能、记忆及工具调用仍待后续实现。现有开发约定以 CLAUDE.md 为准。健康实验记录见 experiments/health_server/README.md；手机安装、部署和验证见 mobile_server/README.md。

## 1. 目标与已知条件

- 安卓设备：小米 14、Android 16、HyperOS 3.0.306；主要数据源为手机自带的“小米运动健康”，用户确认中国版、App 版本 3.57.0。系统 ROM 地区未单独确认，不从 App 地区推断。
- 穿戴设备：小米手环 10（Xiaomi Smart Band 10），用户提供手环版本 3.1.28；该版本不作为手机健康 App 版本。用户已确认小米运动健康能显示心率和睡眠。
- 用户已选择较快完成、尽可能复用现有界面：采用 Kotlin + WebView 路线，不进行全原生 UI 重写。
- 用户已接受数据处理策略：自有服务器可处理业务数据；健康数据发给模型分析单独开关、默认关闭，启用后只发送必要摘要。
- 手机可独立聊天、浏览历史和附件，电脑关机不影响手机聊天。
- Windows/macOS 桌面端与安卓端通过用户自有服务器自动同步应用数据，逐步替代坚果云目录。
- 自动采集可获得的步数、心率等数据，提供每日汇总、趋势和提醒。
- 暂不开发 iOS；第一阶段按个人自用、单用户多设备设计。
- 服务器：47.102.146.139。本轮前的只读检查已确认 SSH 密钥可用；Ubuntu 22.04.5，约 1.6 GiB 内存、约 30 GiB 空闲磁盘。80/443 及其他端口已有服务，所属进程、反向代理、域名与证书尚未检查清楚。
- 以上资源足以作为轻量个人服务的起点，是容量判断而非压测结论；不在这台机器上部署本地大模型。

## 2. 现有代码与迁移约束

| 现状 | 对方案的影响 |
| --- | --- |
| pywebview 前端经 window.pywebview.api 调用 Python，Python 通过 evaluate_js 推送 | 需要拆出 UI 无关的聊天服务和明确的客户端接口，不能直接把整个 API 类暴露到公网 |
| app/sync.py 依靠 copy2 和 mtime 复制本地目录 | 必须增加版本、增量游标、冲突与删除协议，不能只替换同步路径 |
| 对话、配置、记忆及平铺的技能 Markdown 已有目录同步 | 可做迁移入口，但图片、附件、用量等需扩展 |
| 会话含绝对路径、工具历史、图片快照、文件 diff | 云端使用附件 ID 与设备路径映射，保留桌面原有语义 |
| 普通 script 共享全局作用域，存在加载顺序约束 | 第一版复用前端时不顺带进行全面框架重写 |
| 历史消息内容要求稳定，以保持模型前缀缓存 | 同步不能随意改写历史正文；跨设备附件在请求边界解析 |
| 临时会话不持久化、不进入同步 | 服务端也不落盘临时会话，日志不得留下正文 |
| 工作区已有未提交修改 | 实施前核对差异，保留用户改动，不覆盖既有工作 |

## 3. 健康数据接入：先解决能否读取，再承诺功能

### 3.1 已核实的官方信息

**小米端侧 SDK**：当前官方指南要求 HyperOS 4.0 或以上、中国大陆支持范围，以及可访问的系统 HealthKit 服务；还需应用注册、签名配置和授权。后台、息屏及频率限制也会影响调用。因此 Android 16 本身不能证明可用。[小米客户端指南](https://dev.mi.com/xiaomihyperos/documentation/detail?pId=2332)

**小米云端 API**：官方提供账号授权和健康数据接口，使用前需开通账号服务、运动健康服务并通过权限审批。能看到文档不等于个人应用已获准接入；个人申请资格、具体权限与实际数据覆盖须在开放平台核实。[小米服务端指南](https://dev.mi.com/xiaomihyperos/documentation/detail?pId=2333)、[云服务接口](https://dev.mi.com/xiaomihyperos/documentation/detail?pId=2328)

**Health Connect**：Android 官方有设备与 Google Play 服务要求；Android 14 以上的系统集成也不能推导出当前国行 ROM 和小米运动健康一定可互通。需要同时确认 Health Connect 可用，以及小米 App 确实写入目标数据。[可用性说明](https://developer.android.com/health-and-fitness/health-connect/availability)

旧版“小米健康云”资料不能代替上述新接口的准入与兼容性结论。当前未在用户手机上验证任何健康接口。

### 3.2 候选路线

| 路线 | 优点 | 前提与不足 | 建议 |
| --- | --- | --- | --- |
| 官方小米云端 API → 自建服务器 | 健康拉取不依赖 QuickModel 安卓 App 一直运行 | 需开发者准入和权限审批，个人申请受限 | 不作为当前交付前提 |
| 非官方小米云端读取 → QuickModel | 可继续使用原 App，不需要健康平台开发者凭据 | 需用户账号会话；接口与登录可能失效，具体项目尚未审计 | 推荐下一阶段优先评估，不视为已选定或已验证 |
| Gadgetbridge 蓝牙读取 → 自动导出 → QuickModel | 不依赖健康云开发者接口或 Health Connect | 手环 10 支持仍有实验性，需配对密钥，可能与原 App 抢同步 | 用户接受改变配套 App 时的备选 |
| 小米端侧 SDK → 安卓 App → 自建服务器 | 直接使用小米官方本地数据接口 | 官方要求 HyperOS 4.0+，当前为 3.0.306 | 当前首版不依赖此路线，未来条件满足再评估 |
| 小米 App → Health Connect → 安卓 App | 后续适配其他安卓品牌更方便 | 用户系统搜索不到入口，App 三方管理截图也无此项 | 不作为当前首版依赖；未来设备条件改变时再评估 |
| 用户导出数据后导入 | 官方自动通道不可用时仍可保留记录 | 需确认真实导出格式；不是自动监测 | 明确标为降级功能 |
| 手机传感器自行计步 | 可采集本 App 的步数 | 不是小米历史数据，重启/采样/跨日需处理；不能补出心率 | 可选独立功能，不用于冒充完整接入 |

不把读取其他 App 私有数据库或保存小米账号密码作为基础路线。v0.4 根据用户关于无开发者账号方案的请求，将使用本人账号的非官方云接口纳入候选；此前不采用私有接口的建议不再排除对此路线的评估。是否采用仍须讨论，不执行登录或安装。

### 3.3 当前设备结论与待确认事项

已确认存在真实心率和睡眠记录，剩余问题是第三方读取通道，不是手环是否采集。当前系统不满足上述端侧 SDK 文档要求，不能将系统升级作为快速交付的前提，也不建议为本项目更换 ROM 或解绑手环。

用户提供的中国版 3.57.0 截图显示：

- 数据来源：Zepp Life、小米电视。
- 分享服务：微信（文字明确为步数同步）、支付宝。
- 账号数据授权：小米电视、北大国际睡眠服务、蚂蚁阿福。
- 用户在系统设置搜索不到 Health Connect / 健康连接；截图中也没有该入口。

这些证据足以将 Health Connect 移出当前首版依赖，但不等同于通过系统包检查证明其组件绝对不存在。Zepp Life 位于“数据来源”，不能推断小米手环 10 的心率和睡眠可反向导出给它。其他第三方项目的出现也不能证明自建应用可以直接取得同等权限；不将微信步数分享误当作完整健康 API。

官方小米云端 API 列有步数、心率、睡眠只读权限，但仍需开发者服务开通和审批。[官方权限与授权说明](https://dev.mi.com/xiaomihyperos/documentation/detail?pId=2333) 用户提供的注册标准明确写明“小米应用商店暂不接受个人开发者账号申请”。该条文字面针对应用商店，不能据此断言所有小米服务都不接受个人，但目前没有查到可保证健康服务个人准入的例外；因此不再把申请成功当作交付前提。[注册标准](https://dev.mi.com/xiaomihyperos/documentation/detail?pId=1731)

下一项方案工作改为比较无开发者账号候选，见 3.5；不要求用户为本项目注册企业。官方渠道保留为未来可替换的数据源。

当前尚无在用户账号与手环固件上验证通过的自动采集路线。新发现的开源实现提供了验证方向，不等同于保证可用；不把手动导入计为完成自动监测，也不要求用户切换 App 地区或刷机。

聊天和同步不应依赖健康 SDK 才能构建；健康模块通过独立数据源接口接入。是否先交付聊天/同步、待通道明确再交付健康模块，作为交付顺序建议供本轮讨论，不代表已取消自动健康目标。

### 3.4 数据与产品语义

- 首批争取步数、心率；睡眠作为下一项，有真实来源才启用。无记录显示“暂无数据/未授权/尚未同步”，不显示为 0 或“正常”。
- 保存来源、设备、原始记录 ID、采样区间、单位、时区、更新时间、采集通道和修订状态。
- 同一小米记录同时经过云端和 Health Connect 时不能累加；每类指标确定主来源，跨通道匹配不可靠时保留原记录并只用主来源汇总。
- 步数累计值与增量值分开处理；跨日按记录时间和时区计算。平均采样心率不能标成静息心率。
- 数据修订、撤销与晚到记录触发对应日期重新聚合；日报标注覆盖情况及最后同步时间。
- 自动任务建议数小时一次并在打开 App 时补同步；具体周期按数据源限制确定。WorkManager 周期任务最短 15 分钟且可能延迟，不能保证准点执行。[Android 后台任务说明](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)
- 首版提供趋势、步数目标和可配置提醒；不承诺实时医疗预警。AI 解释使用选定日期的摘要，并显示数据不足情况。

### 3.5 无开发者账号的实现候选（v0.4）

**A. 非官方云接口：优先评估，尚未采纳。** 保留“手环 → 小米运动健康 → 小米云”，由用户授权的采集器读取自己的数据。候选项目 [mi-fitness-mcp-cn](https://github.com/HUAYUE1024/mi-fitness-mcp-cn) 自述支持中国区、扫码登录、心率/睡眠和增量同步；明确声明采用逆向接口。这里仅核对了项目说明，未审计源代码、运行测试或确认当前账号兼容性。其登录会话与官方细粒度健康 OAuth 不同，可能具有更广账号能力；不能把“不保存密码”理解为没有凭据风险。

建议登录会话优先留手机，手机向自建服务器上传选定健康记录；若采用 Python 采集器常驻自有服务器，可减少手机后台限制，但需另行确定是否接受服务器持有小米会话。既有“服务器可处理健康数据”的选择不自动等于同意托管小米账号会话。手机实现需额外适配成本；桌面采集实现较快但电脑关机会停止采集。

另一个参考 [Better Mi Fitness Sync](https://github.com/ilyasaftr/better-mi-fitness-sync) 自述支持从账号读取健康数据与定时同步，但现成安卓版本依赖 Health Connect；不能直接承诺安装即可解决本设备的问题。可在许可证和源码审查后评估其采集层，输出改为 QuickModel 是未来开发工作。

验证门槛：先审查网络目的地址、登录/凭据保存、许可证和依赖；再由用户自行完成登录，以只读方式对照一天的步数、心率、睡眠及多日补传。接口失效、验证码或会话过期要明确提示重新登录，不能绕过登录校验或静默给出零值。不将第三方示例中的明文凭据回退直接用于服务器。

**B. Gadgetbridge：直接蓝牙备选。** 官方设备列表将手环 10 标为“大部分支持”且实验性，需要小米配对密钥；与用户固件 3.1.28 的兼容性未验证。[设备列表](https://gadgetbridge.org/gadgets/wearables/xiaomi/) 项目支持数据库定时导出，QuickModel 可经用户授权目录读取导出快照并解析上传，不必经过 Health Connect。[自动导出](https://gadgetbridge.org/internals/automations/auto-export/) 其同步文档提醒避免原厂 App 同时同步并移除设备数据，因此不能承诺与小米运动健康稳定共存。[同步说明](https://gadgetbridge.org/basics/features/sync/) 睡眠算法、历史覆盖与官方 App 结果可能不同，必须对照验证。优先进程间导出集成，嵌入源码前另核许可证。

**C. 官方个人数据导出：低改动兜底。** 小米官方提供账号隐私页中的 Mi Fitness 数据下载流程，无需健康开发者凭据。[官方导出说明](https://www.mi.com/ph/support/article/KA-11566/) 当前中国账号入口、导出内容和格式仍需查看实际样本。可做导入解析与去重，但导出准备和用户下载不是可靠每日自动 API。

屏幕截图/OCR可做用户主动分享后的摘要录入，不适合持续获取完整采样序列；无障碍定时抓屏、Root 私有数据库与强行切国际版均不作为快速稳定交付路线。

## 4. 安卓技术选型

| 方案 | 适用性 | 成本与取舍 |
| --- | --- | --- |
| Kotlin + WebView 复用聊天界面 | 推荐作为第一版 | 最大化复用 Markdown/LaTeX 等现有代码；仍需移动布局、桥接和滚动/键盘适配 |
| Kotlin + Jetpack Compose 全原生 | 若优先长期原生体验可选 | UI 和聊天渲染需要重写；健康 SDK 仍可直接接入 |
| Flutter | 有跨平台目标时再考虑 | 当前只做安卓，新增 Dart 技术栈，同时仍要处理小米 SDK 的原生桥接 |
| PWA/手机网页 | 可作为远程聊天入口 | 不承担本项目所需的原生健康数据接入与可靠后台任务 |

已选组合：Kotlin 管理登录、网络、本地数据、文件选择、健康权限、任务和通知；WebView 复用现有聊天、Markdown/LaTeX 和适合手机的设置呈现。为减少首版工作量，健康统计和普通设置也优先使用网页界面；授权、文件选择等系统交互仍用原生能力，不额外引入一套全原生页面体系。

前端增加有限的平台适配层，将桌面 pywebview 和安卓桥接实现放到明确边界。只复用移动端实际需要的接口；不模拟整个桌面 API，也不在本次改造中引入 React/Vue 或重写现有 script 加载结构。

- 本地存储候选为 Room（SQLite），用于离线历史、待同步队列和游标；不把大量聊天历史和密钥存进 localStorage。[Room 官方文档](https://developer.android.com/training/data-storage/room)
- 页面资源随 APK 分发，外链用系统浏览器；桥接只允许应用自身 origin 和主框架，使用有限方法和严格参数校验。官方当前建议评估 addWebMessageListener。[Android 桥接说明](https://developer.android.com/develop/ui/views/layout/webapps/native-api-access-jsbridge)
- 模型输出按不可信内容处理：Markdown HTML 清洗、禁用任意脚本/iframe、限制链接协议；桥接限制不能代替 XSS 防护。[WebView 安全说明](https://developer.android.com/privacy-and-security/risks/insecure-webview-native-bridges)
- 手机默认关闭桌面高开销天气/背景特效；重点适配软键盘、返回手势、附件、选择复制、长对话和断线恢复。
- SDK/Gradle/Kotlin 具体版本在路线确认后按真实小米 SDK 依赖锁定，不照抄文档中的旧构建版本。签名证书持久保存，以便升级及小米鉴权。
- APK 先按个人安装交付；公开分发另行评估，不把应用商店上架作为首版前提。

## 5. 服务端与聊天执行

推荐：Python + FastAPI + Uvicorn，SQLite 起步，附件落本地磁盘；systemd 管理进程，接入现有 HTTPS 入口。使用独立虚拟环境和最小依赖集合，沿用仓库 requirements.txt 为依赖约定真源，实施时明确服务器与桌面的安装分组。

| 选择 | 推荐理由 | 何时改选 |
| --- | --- | --- |
| FastAPI | 适合明确的 Python HTTP API，便于复用现有模型调用逻辑 | 若服务需求扩大再评估其他框架，无需先重写语言 |
| SQLite | 个人单机负载，资源和维护成本较小 | 写并发增大、多实例运行时迁移 PostgreSQL |
| 磁盘附件 | 现有容量适合初期使用，减少服务数量 | 容量或可靠性需求增长时迁移对象存储 |
| systemd + 独立环境 | 当前小内存服务器可先保持部署简单 | 用户更重视容器交付时选择 Docker Compose |
| HTTP + SSE | 普通操作走 HTTP，模型输出采用单向流事件 | 未来有大量双向实时协作需求再评估 WebSocket |

以上是本项目的工程建议，不是框架的唯一用法。[FastAPI](https://fastapi.tiangolo.com/)、[SQLite 适用场景](https://www.sqlite.org/whentouse.html)

聊天调用建议手机走服务器代理，桌面默认继续直接调用模型供应商。这样手机关机/切后台后的运行状态可在服务器查询，桌面现有本地工具能力也能保留。

- 抽出 UI 无关的聊天服务与回调事件；不要整体导入桌面窗口 API 充当网络服务。
- 首版服务器只提供聊天及限定的附件处理，不把桌面 run_command、任意文件读写、浏览器操作照搬到公网。
- 请求以 request_id 幂等创建 run_id；断线后重连读取已有事件或最终结果，不重复调用模型计费。停止是独立操作；服务重启后未完成任务标为中断，不暗中重跑。
- 客户端上传时限、模型并发和附件大小应受限；OCR 等重任务延后，避免耗尽现有内存。
- 离线可看缓存、编辑草稿，在线才生成回复；未明确选择自动发送的草稿不在恢复网络后偷偷发出。

## 6. “所有数据”同步的明确边界

目标是全部应用业务数据，而不是整个电脑目录或系统配置镜像。

| 数据 | 计划 |
| --- | --- |
| 持久会话、标题、归档、排序 | 完整同步，保留冲突版本 |
| 图片快照、上传文档、生成图片 | 按内容哈希保存 blob，以附件 ID 引用；缺失历史文件明确列出 |
| 记忆、技能 | 同步用户内容；技能资源按清单与安全相对路径处理，不局限于单个 Markdown |
| 通用模型配置、提示词、偏好 | 字段级区分共享与设备设置 |
| API Key / Token | 推荐服务器密钥库保管；客户端下载配置只含引用和脱敏状态，桌面直连密钥单独迁移策略待确认 |
| 用量 | 新记录独立 ID 并去重；旧记录迁移使用稳定批次/来源标识，无法可靠判重的旧副本单独核对 |
| 健康数据、汇总和日报 | 按数据源权限同步，可撤销上传和删除云端副本 |
| 文件操作历史及 diff 快照 | 作为会话附属数据同步，按体积限制；不据此同步项目源文件 |
| 项目分组 | 共享项目逻辑 ID，各设备维护本地目录映射 |
| 命令白名单、SSH 私钥、设备登录凭据、缓存、日志 | 本机保留；日志仅用于诊断，不属于业务同步 |
| 临时会话 | 不持久化、不同步 |

### 6.1 一致性协议草案

- 服务端保存 entity_id、revision、change_seq、deleted_at；客户端保存上次已应用的游标及本地待发操作。
- push 携带 op_id、device_id、base_revision；服务端事务中校验版本、写实体和变更日志。同一 op_id 重试返回原结果。
- pull 按 change_seq 分页；只有本地事务落盘成功才提交游标。时间戳用于展示，不用作胜负依据。
- 同一会话并发修改时先保留分支/冲突副本，不用“最后上传者覆盖”。模型 tool_calls、摘要和撤回不能按普通文本自动拼接。
- 生成中的会话固定基准版本；新远端内容暂存或形成分支，不覆盖正在写入的内存对象。
- 删除保留 tombstone；首版不自动清理。将来清理须有设备确认水位和过期设备全量重建机制，避免旧设备复活数据。
- 附件分块策略按大小确定，提交前校验长度与哈希，临时写入后原子完成；实体引用与 blob 完成状态可验证。所有附件读写仍需用户授权，知道哈希不能绕过鉴权。
- Windows JSON 落盘也需锁、临时文件和原子替换，防止同步线程与生成线程相互覆盖。导入配置后按现有约定刷新内存。
- 启动、恢复前台、保存后触发增量同步；后台采用退避重试。界面显示最后成功时间、待上传数量、冲突和错误。
- 同一批数据只能启用一种自动同步后端，迁移期间禁止坚果云与服务器同时竞争写入。

### 6.2 兼容旧数据与模型缓存

- 首次迁移先备份并生成清单、数量和哈希；保留原对话文件身份，包括现有冲突后缀。
- 附件绝对路径通过 sidecar 映射关联到统一附件 ID；不批量替换历史消息字符串。
- 请求边界解析原生图片和附件；电脑文件不存在时显示设备归属或缺失信息，不伪造手机路径。
- 切换设备/执行环境可能导致一次模型缓存失效；保证同一环境中后续历史稳定，不承诺跨设备百分百命中。
- 同步失败不会删除本地原数据。回退时先导出服务器新增内容再恢复旧后端，避免遗失迁移后的变化。

## 7. 安全、部署与健康隐私决策

- HTTPS、设备级可撤销会话、登录限流、服务端访问控制；SSH 私钥仅用于运维，不打包进 APK。
- 单用户起步但实体包含 owner_id，避免未来扩展时重新设计隔离。
- 服务器上的模型密钥与小米 OAuth 刷新凭据加密保存，主密钥在代码仓库和数据库备份之外管理；客户端令牌由 Android Keystore 保护。
- 已确认：健康数据上传与“发送给模型供应商分析”分开开关，后者默认关闭；用户启用 AI 日报后仅发送所需摘要。普通聊天仍按聊天功能发送给选定模型供应商，不自动附加健康记录。
- 已确认：首版采用 HTTPS + 服务端受控访问及敏感凭据加密；这不是端到端加密，服务器能够处理用户数据。以后如改为服务器不可读，需重新设计服务端分析与模型代理。
- 部署前只读盘点已有 80/443 服务、域名和证书，再决定复用现有反向代理；应用绑定回环地址，使用独立服务用户、目录和资源限制。
- 首版备份建议每日数据库一致性备份加附件增量，保存到独立故障域；保留周期、备份位置和恢复目标与用户确认。同盘备份不能覆盖服务器丢失。
- 存储配额与磁盘告警、缺失附件检查、数据库恢复演练纳入交付。

## 8. 实施阶段及验收门槛（全部尚未开始）

### P0：路线讨论与健康接入准入确认

- 失败时回到数据源选择；聊天/同步可独立推进，但不得将健康自动接入宣称已完成。

### P2：同步服务与桌面兼容

- 完成鉴权、数据模型、增量协议、附件与旧数据迁移预览。
- 两个独立客户端验证离线修改、并发冲突、删除、重试、生成中同步及恢复。
- 验收：无静默覆盖、附件可校验、游标重放不丢数据、原始数据可回退；临时会话不出现在同步存储。

### P3：安卓聊天 MVP

- 登录、流式聊天、历史、模型选择、附件、本地缓存、自动同步、错误和冲突状态。
- 电脑关机时可用；弱网重连不重复发起模型请求；长回复、停止、退后台、返回前台行为明确。
- MVP 不包含远程控制电脑工具、桌面全部设置和完整动画复刻。

### P4：健康模块

- 接入 P1 通过的通道，完成幂等上传、跨日统计、每日趋势与可选 AI 日报。
- 验证手机/手环重复来源、补传、修订、权限撤回、时间变更、缺失数据和省电限制。
- 连续多天真机观察后再声称具备每日自动采集能力；传感器缺失时不能用模拟数据替代验收。

### P5：试用交付

- 签名 APK、桌面更新、服务安装/回滚说明、备份恢复和一段时间的个人试用。
- 检查服务端内存与磁盘增长、日志脱敏、鉴权失效、附件越权、WebView 内容安全。
- 本计划仅列未来验证项，本轮没有执行任何上述测试或部署。

## 9. 需要讨论的决定

### 当前收敛：先验证服务器健康采集（v0.5）

用户希望先实验效果，选择服务器保存数据以减少开发量。按上一轮选项，方案采用服务器运行采集器、按需加密保存小米登录会话；不开发手机端的小米协议适配。登录仍由用户自行完成，不在聊天中索取密码或 Cookie。

最小实验建议：独立目录、独立环境运行经过审查并固定版本的采集器；先获取最近 7 天步数、心率、睡眠，展示每日汇总、来源覆盖和同步状态；验证重复拉取去重及会话失效提示后，再考虑每 6 小时增量同步。以上为计划，不代表已获取数据或已创建定时任务。手环与原 App 继续负责上传小米云，服务器无法替代这段链路。

实验初期不需要先购买域名：管理页面仅绑定服务器回环地址，通过本机 SSH 隧道访问并展示登录二维码；不向公网直接开放候选项目的登录/API 页面。后续手机远程访问再确定 HTTPS 入口。AI 分析保持关闭，待用户确认采集效果后另行启用。

验收以真实账号数据为准：每日步数、至少一天心率记录和一晚睡眠与原 App 对照；缺失、延迟和口径差异明确展示。成功后将采集器作为独立数据源接入 QuickModel，继续原定安卓聊天与全量业务数据同步目标，不在验证前重构主应用。

第三方审查关注登录请求去向、凭据是否明文落盘或出现在日志、接口鉴权、网络暴露及许可证。源码获取或审查不等于安装执行，尚未运行第三方程序。
